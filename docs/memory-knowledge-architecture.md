# 记忆与知识架构详解（核心技术点汇编）

> 日期：2026-08-09 · 来源：设计问答讨论的系统化沉淀
> 定位：本文是记忆/知识子系统的**原理与决策依据详解**。选型结论的 SSOT 仍在
> `storage-selection.md` 与总体设计 AD 表；本文与之冲突时以 SSOT 为准。
> 实现细化落在 spec-3.4/3.5/3.6。

## 1. 记忆库为什么选 Graphiti

**核心理由一句话：运维记忆的本质是时间线，Graphiti 是目前唯一把"时间"作为一等公民的
开源记忆方案。**

### 1.1 双时间线模型正中运维场景

Graphiti 图谱中每条事实（边）带 `valid_at / invalid_at`（现实中何时成立/失效）与摄入
时间。新信息与旧事实矛盾时**不删除旧事实，而是打失效时间戳**——历史保留为可查询的
时间线。运维记忆"实例→症状→根因→处置→效果"正是这种带时间轴的因果链：8 月症状再现时，
agent 可查"上次何时出现、怎么处理、有效吗"，并发现"两个月内第二次复发"的模式。

### 1.2 备选方案的短板

| 方案 | 短板 |
|---|---|
| Mem0 / 纯向量记忆 | 无因果结构与时间线；矛盾新旧事实并存且同被召回（"索引已重建"与"索引失效"并存，无从判断现状） |
| GraphRAG（微软） | 为静态语料批处理设计，增量更新要重算；agent 记忆是持续流（每次会话/巡检），成本不可接受 |
| Zep Cloud | 客户数据出境，合规否决 |
| 自建 pgvector | 只有"找相近"，没有"何时、为何、结果如何" |

### 1.3 工程加分项与代价

加分：混合检索路径上无 LLM（毫秒级、低成本，agent 每 turn 查记忆不成瓶颈）；
Pydantic 自定义实体类型可对齐运维本体（Instance/Incident/Remediation/Baseline）；
group_id 原生多租户；跑在 Neo4j 上与知识图谱共用基础设施（AD-6），且支持 FalkorDB
后端（解耦点 R4 替换路径）。

代价与缓解：摄入侧需 LLM 做抽取——走异步管道 + 网关路由便宜模型；Python 栈且项目较
年轻——包在记忆服务 API 后面（解耦点 R3），换实现不动接口。

## 2. Graphiti 与 Neo4j 的关系及数据模型

**Graphiti 是记忆引擎（Python 库），不是存储；Neo4j 是存储后端**。Graphiti 定义数据
模型、负责写入加工与检索编排，所有数据物理存在 Neo4j。

Neo4j 中的图对象（全部带 group_id 租户命名空间）：

| 图对象 | 内容 | 作用 |
|---|---|---|
| Episode 节点 | 原始输入完整留档（会话原文、巡检结论） | 数据源头，可重建、可审计溯源 |
| Entity 节点 | 抽取实体 + 摘要 + 名称 embedding | 图的骨架（自定义类型对齐运维本体） |
| RELATES_TO 边 | 主谓宾事实 + 事实 embedding + valid_at/invalid_at | 记忆主体，时序失效作用层 |
| MENTIONS 边 | Episode → Entity 提及关系 | 证据链（这条事实是哪份巡检说的） |
| Community 节点 | 实体聚类 + 社区摘要 | 高层概览 |
| 向量/BM25 索引 | 实体名/事实/摘要 | 三路混合检索的物理基础 |

**硬纪律（进开发规范）**：业务代码禁止绕过 Graphiti 直写 Neo4j——去重、实体合并、
时序失效是 Graphiti 写入管道维护的不变量，直写会制造重复实体与僵尸事实。
Neo4j 直查仅限：控制台图谱可视化（Cypher 只读）、记忆质量排查、存储运维。

## 3. 检索机制：三路混合召回 + 重排（图和向量都用）

1. **向量检索**：查询 embedding 对事实/实体/摘要 embedding 余弦召回（Neo4j 向量索引）；
2. **BM25 全文**：关键词召回，补精确词短板（实例名、错误码、参数名——运维场景极多）；
3. **图遍历**：从中心节点（当前会话涉及的实例实体）BFS 展开邻域，靠结构关联而非文本相似。

三路 RRF 融合，可选**图距离重排**（按候选到中心实体的图上距离）、MMR 去冗余、
cross-encoder 精排。时间过滤器按 valid_at 筛"当前有效"或按区间查历史。
**检索全程无 LLM**（LLM 只在摄入侧），查询是毫秒级数据库操作。

## 4. 记忆分层、归属与沉淀（SSOT：storage-selection.md §1.1）

- **双层记忆**：常驻指令层（CLAUDE.md 职能的平台化——agent/租户 markdown 指令文档存
  控制面 PG，版本化，每 turn 确定性注入）+ 检索层（Graphiti，按需混合检索）。
  不做记忆双写 md，Episode 原文即 SSOT；
- **实体中心归属**：记忆归"租户 + 实例实体"所有，无 agent 私有图命名空间——实例历史是
  客观事实，换 agent 接管零成本；agent 个性化偏好放常驻指令层；
- **命名空间**：`platform`（通用运维知识）/ `tenant:{id}`（租户记忆）同库硬隔离，
  检索时两区并查、结果带来源标签合并；
- **沉淀管道（合规红线）**：租户记忆 → platform 通用知识必须经脱敏→泛化→审核，禁止自动流动。

## 5. 记忆全链路与容器无状态下的连续性

### 5.1 写路径与读路径

```
写：turn 结束 → runtime 异步送 episode → Graphiti（LLM 抽取→去重合并→时序失效→embedding）
    → Neo4j（原料 Episode + 加工品图谱两层并存）
读：turn 开始 → runtime 自动检索（固定环节，不靠模型自觉）→ 三路混合 → 注入上下文
```

对比 CC/codex：二者的原生记忆是本地文件/状态、不可换后端；接 Graphiti 只能走 MCP
工具形态（存取靠模型自觉调用、摄入拿不到完整会话流）。**把记忆做成 runtime 基础设施
而非可选工具，是 AD-11 自有 runtime 的核心理由之一。**

### 5.2 场景走查：容器启停后新 pod 接管数据库

agent 是控制面里的逻辑实体（AD-1），容器只是无状态执行体——pod 死掉，agent 不死：

1. Pod A 诊断 prod-mysql-03，episode 入图，会话入 threadstore-PG；
2. Pod A 被回收——配置/会话/记忆全在外部存储，零丢失；
3. 新任务路由到 Pod B，加载 agent 配置（绑定实例、挂载 skill、指令文档）；
4. runtime 以实例实体为中心检索 tenant+platform 命名空间 → 取回故障时间线、负载特征；
5. agent 带完整历史工作：周日凌晨高负载不误报（记忆有"跑批属正常"），
   熟悉症状直接给上次有效方案。

甚至删掉 agent X 新建 agent Y 接管同一实例，Y 照样检索到全部历史（实体中心归属）。
会话进行中 pod 死亡另有**会话内连续性**兜底：rollout 为 SSOT，其他 pod 恢复续跑。

### 5.3 agent 状态全景（身份/配置/会话/记忆分别在哪）

| 状态 | 存储 | 内容 | 丢失后果 |
|---|---|---|---|
| 身份+配置 | 控制面 PG（RLS） | agent_id/租户、绑定实例、挂载 skill、巡检策略、指令文档 | 不允许丢 |
| 会话 | threadstore-PG | 线程元数据（UUID7）+ rollout 事件流（**SSOT**） | 不允许丢 |
| 上下文热缓存 | Redis | 进行中 turn 工作上下文、检索缓存、幂等键（TTL） | **可丢**，从 rollout 重建 |
| 记忆 | Neo4j（Graphiti） | 时序知识图谱 + Episode 原文 | 不允许丢 |

持久层仅三个备份域：控制面 PG 全家桶、Neo4j、对象存储；pod 本地零持久状态——
这是 k8s 随意启停扩缩的前提。"负载特征"双存储：数值基线在 TimescaleDB（spec-3.7），
解释性经验（"周日高负载是跑批"）在 Graphiti。

## 6. 知识库侧：文档管道与双向量索引

### 6.1 文档摄入管道（进 pgvector 的路，对应 spec-3.6）

```
上传（客户 runbook / 平台内置手册）→ 格式解析 → 清洗 → 切片（标题结构+尺寸+重叠）
  → embedding → 写 pgvector（chunk + 向量 + tenant_id/doc_id/章节路径/模型版本）
```

**5 步里 4 步是确定性代码**（知识库服务 Python worker），唯一模型调用是 embedding
（编码器，非 LLM）。与 Graphiti 摄入对比：文档是静态权威文本，无需抽取/去重/时序失效，
更新 = 按 doc_id 整篇重切重嵌。可选 LLM 增强（烂 PDF 表格抽取、上下文增强切片、
文档摘要）不在基线管道，实测检索短板后按需加。

### 6.2 双向量索引并存 = "向量跟着数据走"

| | Neo4j 向量索引 | pgvector |
|---|---|---|
| 向量内容 | 图谱内实体/事实/摘要 embedding | 文档切片 embedding |
| 使用方 | Graphiti 三路检索之一 | 知识检索 API 文档 RAG |
| 为何不合并 | Graphiti 混合检索要求向量与图遍历同引擎；拆开=每次记忆查询跨系统 join | 文档靠 PG RLS 隔离；进 Neo4j 丢 RLS、加重记忆关键路径、且用不上图能力 |

**运维成本没有"多一套系统"**：两处都是既有存储（PG、Neo4j）的内建索引，非新增部署物。
文档侧超出 pgvector 舒适区时按解耦点 R5 单独换 Qdrant，图谱侧不受影响。

### 6.3 客户本地知识库

默认：平台侧三层租户隔离存储（对象存储原文件 + pgvector 切片 + Graphiti 结构化知识，
客户知识与实例记忆同图谱可关联）。高合规变体（Stage 4 选项）：Connector 内嵌本地检索
模块（SQLite+sqlite-vec + bge-small 级 ONNX 模型），平台 agent 经隧道当 MCP 检索工具
调用，只回传 top-k 片段，全文库不出内网——复用 AD-3"计算下沉、结论上行"模式。

## 7. embedding 模型：部署形态与选型

### 7.1 部署位置：独立服务，不在 agent 里

agent-runtime 是 Go 进程，无任何 ML 运行时，也**不直接调用 embedding**——向量化发生在
记忆服务/知识检索 API/文档摄入 worker 内部（解耦点 R3/R5 边界）。embedding 模型经
LLM 网关统一接入（LiteLLM 同时代理 chat 与 embeddings 端点），实体是网关后独立的
推理服务（自托管 BGE-M3，TEI/Infinity 框架）或云 API。
唯一进程内嵌例外：Stage 4 Connector 本地小模型（§6.3）。

### 7.2 选型要点

- embedding 是厂商服务的一种，但不是每家都有（Anthropic/DeepSeek 无自家 embedding API）；
  开源自托管（BGE/GTE/E5）在中文检索上打平甚至优于商用 API；
- **自托管 BGE-M3 为主路径的战略理由**：Stage 4 私有化打包需要离线 embedding，
  自托管使 SaaS 与私有化用同一模型，避免私有化时客户知识库全量重建；
- **一致性硬约束**：同一库的建索引与查询必须同模型同版本；每行记录模型版本；
  换 embedding 模型 = 有计划的全量重嵌工程。

### 7.3 chat 模型与 embedding 模型的更换互不影响

chat 模型消费的是检索出的**文本片段**，从不接触向量——换 chat（DeepSeek↔Qwen↔Claude）
对向量库零影响，网关动态路由随意切；只有换 embedding 模型本身才触发全量重嵌。
因此设计上：chat 层做动态路由（按任务分档），embedding 层锚定单模型 + 版本入库。

## 8. 会话存储：threadstore-PG 与 rollout 事件流

### 8.1 存储形态

codexgo 本地形态（rollout JSONL 文件 + SQLite + threadstore local 实现）换为
**PostgreSQL 后端**（spec-1.8 核心改造，接口已抽象）。与控制面同 PG 集群不同 schema：
事务一致、RLS 直接生效、同一备份域。概念表形态：

```
threads         thread_id(UUID7) / tenant_id / agent_id / title /
                parent_thread_id(子agent关系) / status / 时间戳
rollout_events  thread_id / seq / turn_id / event_type / payload(JSONB) / created_at
                （append-only 事件日志；恢复会话 = 按序重放）
```

### 8.2 rollout 记录什么（不只是聊天+工具调用）

rollout 是 **turn 执行的完整事件日志（event sourcing）**，聊天记录只是可见子集：
对话事件、工具事件（参数+结果）、推理事件、**会话元事件**（配置快照、每 turn 模型参数
与 token 用量）、**压缩事件**（上下文压缩的标记与摘要）、**审批事件**（AD-9 链路）、
异常/中断事件、子 agent 事件。

三个刚需各对一类：**恢复正确性**（重建"模型当时看到的精确上下文"需要压缩事件与配置
快照，只有聊天记录会导致重放漂移）；**审计**（审批与工具事件是证据本体）；
**计费**（token 用量按 turn 聚合成租户账单）。类比：聊天记录之于 rollout ≈ 银行 App
流水页之于总账凭证——线程列表、Redis 上下文、聊天界面都只是这份日志的投影。

## 9. rollout 体量治理

量级估算（数量级）：单 turn 20-100KB（大头是工具结果）、诊断会话 0.5-2MB、
巡检会话 1-3MB、租户/天 50-150MB、100 租户/年原始量 **2-5TB**——必须治理。四层手段：

1. **工具结果引用化（最有效）**：采集数据本就在 TimescaleDB，rollout 只存
   "调用参数 + 结果摘要 + 数据指针"，inline 上限 32KB 超出截断留指针
   （继承 codex 0.138"压缩时重写超大工具输出"思路，同步簇 E）；
2. **存储压缩**：PG TOAST + lz4 对高重复 JSONB 再打 3-5 倍折扣；
3. **分区 + 分级保留**：按月分区；人工诊断会话热保留 90 天，巡检会话 7-30 天
   （结论已沉淀进报告与记忆库，rollout 本体查询价值速降）；
4. **冷归档（Stage 4）**：过期分区压缩归档对象存储（成本 ≈ PG 的 1/20），PG 留
   元数据+归档指针，合规长保留在归档层满足。

治理后稳态：100 租户规模 PG 热数据集稳定在几百 GB（分区滚动，不随时间线性涨）。
落点：spec-1.8（事件模型/引用化/尺寸上限）、spec-0.6（分区与保留策略框架）、
Stage 1 验收实测校准。

## 10. 上下文装配与 Redis 热缓存

**装配是每 turn 的固定流程，Redis 缓存的是装配结果物**：

```
rollout（持久，事件形态）→ 重放 + 应用压缩事件 → 注入常驻指令 + 检索到的记忆
  → 模型消息序列（模型阅读的格式，衍生视图，可确定性重建）
```

Redis 三类内容：装配好的会话上下文（连续 turn 增量追加，免全量重放）、
检索结果缓存（相邻 turn 复用）、幂等键与会话锁。**可丢的原因**：全部可从 rollout
冷装配一字不差地重建，丢失只付一次重放延迟——正确性锚 rollout，性能锚 Redis。
注意与 LLM 厂商侧 prompt cache（KV 缓存，推理层计费优化，网关处理）是上下游关系，
互不替代。

## 11. 容灾设计（按数据分级，不一刀切）

| 存储 | 容灾机制 | RPO 目标 |
|---|---|---|
| 控制面 PG（含 pgvector/TimescaleDB/threadstore） | 主备流复制 + WAL 归档 + PITR | ≈0 |
| Neo4j | 见下文分阶段方案 | 小时级（可重建数据） |
| Redis | 不做数据容灾（可丢层，哨兵/集群只为可用性） | ∞ |
| 对象存储 | 云服务多副本/跨 AZ | 由 SLA 保证 |

- **pgvector 无独立容灾问题**：它是控制面 PG 的扩展，向量随 WAL 物理复制，PG 的
  主备/备份天然覆盖（同栈红利）；且向量可从对象存储原文全量重嵌，等级比"不可丢"更宽松；
- **Neo4j 分阶段**：Community 版无集群复制、在线备份是 Enterprise 功能——
  Stage 3 起步期用 `neo4j-admin dump` 定时备份推对象存储 + CSI 卷快照（小时级）+
  **重放兜底**（Episode 源头在 PG 的 rollout 与巡检报告中，灾难时可重新摄入重建图谱，
  代价是 LLM 费用与时间，信息不灭——这也是记忆 RPO 放宽到小时级的依据）；
  GA 期二选一：Enterprise 因果集群（授权费由商业化收入覆盖）或走解耦点 R4 换
  FalkorDB（自带主从复制 + RDB/AOF）；
- **纪律**：恢复演练进验收——spec-3.10 的 DoD 须含"从备份恢复 + 从 PG 重放重建"
  两条路径实测。
